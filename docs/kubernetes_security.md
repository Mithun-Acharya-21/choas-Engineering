# ChaosEngine AI — Kubernetes Security Architecture & Hardening Guide

## 1. Multi-Tenant Threat Model & Defense-in-Depth

ChaosEngine AI operates as a multi-tenant platform executing controlled chaos fault injection inside Kubernetes clusters. This introduces unique security challenges:
- Experiments intentionally degrade service health and inject latency or packet loss.
- Tenants must never be capable of impacting other tenants, escaping their sandboxes, or accessing cluster control-plane APIs.
- Users must never be permitted to target system or production namespaces.

To eliminate cross-tenant contamination and privilege escalation, ChaosEngine AI enforces a **five-layer defense-in-depth architecture**:

```
Layer 1: Application-Level Safety Boundaries (Namespace Prefix & Catalog Whitelist)
   │
Layer 2: Multi-Tenant RBAC Authorization (Owner, Engineer, Viewer Scoping)
   │
Layer 3: Kubernetes Namespace-Scoped RBAC & Token Disabling (automount=false)
   │
Layer 4: Network Isolation (Default-Deny Ingress/Egress NetworkPolicy)
   │
Layer 5: Compute & Node Protection (ResourceQuota, LimitRange, Pod Security Standards)
```

## 2. Layer 1: Namespace Naming & Target Protection

### Server-Controlled Namespace Generation
Namespaces are strictly generated by the backend API:
```python
def generate_sandbox_namespace(tenant_slug: str, sandbox_id: UUID) -> str:
    cleaned_slug = re.sub(r"[^a-z0-9-]", "", tenant_slug.lower())[:24]
    short_uuid = str(sandbox_id).replace("-", "")[:8]
    return f"sandbox-{cleaned_slug}-{short_uuid}"
```

### Prohibited Namespaces
The validation module rejects any request targeting protected namespaces with HTTP 400 (`SandboxSafetyViolation`):
- `default`
- `kube-system`
- `kube-public`
- `kube-node-lease`
- `chaos-control-plane`
- Any namespace starting with `prod-`, `production-`, `live-`, `stage-`, `staging-`
- Any namespace not strictly beginning with `sandbox-`

## 3. Layer 2: Pod Security Standards (PSS)

Every sandbox namespace enforces the Kubernetes **Baseline** Pod Security Standard using admission labels:

```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/audit: baseline
    pod-security.kubernetes.io/warn: baseline
```

### Mitigations Enforced by Baseline
- **No Privileged Containers**: `securityContext.privileged: true` is rejected.
- **No Host Namespaces**: `hostNetwork`, `hostPID`, and `hostIPC` sharing are blocked.
- **No Host Volume Mounts**: Mounting host filesystem directories (`hostPath`) is strictly forbidden.
- **No Dangerous Linux Capabilities**: Enforces dropped `CAP_SYS_ADMIN` and blocks capability additions beyond the baseline set.

## 4. Layer 3: ServiceAccount & Kubernetes API Confinement

By default, Kubernetes mounts an API token into every container under `/var/run/secrets/kubernetes.io/serviceaccount`. If an attacker or untrusted process compromises a container, this token can be leveraged to query the Kubernetes API server (`https://kubernetes.default.svc`).

### Hardening Applied
1. Every sandbox namespace creates a dedicated `ServiceAccount` with:
   ```yaml
   apiVersion: v1
   kind: ServiceAccount
   metadata:
     name: sandbox-sa
   automountServiceAccountToken: false
   ```
2. Pod templates explicitly disable token mounting:
   ```yaml
   spec:
     serviceAccountName: sandbox-sa
     automountServiceAccountToken: false
   ```
3. Even if a pod crafts raw HTTP requests to `kubernetes.default.svc`, no Bearer token exists in the container filesystem.

## 5. Layer 4: Network Isolation (NetworkPolicy)

The platform applies a strict `default-deny-isolate` NetworkPolicy to every provisioned namespace.

### Policy Rules Breakdown

| Direction | Source / Destination | Allowed Ports | Purpose |
| :--- | :--- | :--- | :--- |
| **Ingress** | Pods in same namespace | All Ports | Intra-sandbox service-to-service communication |
| **Ingress** | Platform Chaos Controller | TCP 8474 | Injected Toxiproxy sidecar management API |
| **Egress** | Pods in same namespace | All Ports | Intra-sandbox service-to-service communication |
| **Egress** | Cluster CoreDNS (`kube-dns`) | UDP 53, TCP 53 | DNS resolution for local service discovery |
| **Egress** | OpenTelemetry Collector | TCP 4317 | OTLP telemetry trace and metric export |

All other ingress and egress traffic (including cross-namespace pod communication, traffic to cloud metadata services `169.254.169.254`, and internet access) is blocked by default.

## 6. Layer 5: Resource Quotas & Limit Ranges

To prevent Denial of Service (DoS) or "noisy neighbor" starvation across shared cluster nodes, every sandbox is bound to a `ResourceQuota` and `LimitRange`:

### ResourceQuota (Standard vs Stress Lab)
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: sandbox-quota
spec:
  hard:
    requests.cpu: "2"
    limits.cpu: "4"
    requests.memory: "4Gi"
    limits.memory: "8Gi"
    pods: "20"
    services: "10"
```

### LimitRange Defaults
```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: sandbox-limits
spec:
  limits:
    - type: Container
      default:
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "2"
        memory: "2Gi"
      min:
        cpu: "20m"
        memory: "32Mi"
```

## 7. Layer 6: Approved Container Image Catalog

To prevent users from running untrusted, malicious, or cryptocurrency-mining container images, the backend enforces an **approved image catalog**:

```python
APPROVED_IMAGE_PREFIXES = (
    "chaosengine/",
    "ghcr.io/shopify/toxiproxy",
    "docker.io/otel/opentelemetry-collector",
    "docker.io/library/nginx",
    "docker.io/library/redis",
    "docker.io/library/postgres",
)
```

Any attempt to deploy unapproved container images is rejected before Kubernetes manifests are submitted to the cluster.
