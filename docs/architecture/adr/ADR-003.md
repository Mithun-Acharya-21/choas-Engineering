# ADR-003: Background Job Architecture

## Context
Platform operations such as spinning up Kubernetes namespaces (30-45s), running controlled chaos experiments (60-300s), and sweeping orphaned resources cannot execute inside synchronous HTTP API request cycles.

## Problem
We need an asynchronous, distributed task execution system capable of running long-lived jobs, retrying failed operations with exponential backoff, enforcing execution deadlines, and recovering gracefully from worker crashes.

## Decision
Adopt **Celery** with **Redis 7** as the message broker and result backend. Combine with **Celery Beat** for periodic watchdog sweeps and Redis distributed locks for concurrency control.

## Alternatives Considered
- **Custom Asyncio Worker Loop:** Simple to write initially, but requires reinventing task persistence, process supervision, retry backoff, dead-letter queues, and distributed heartbeats.
- **Apache Kafka + Custom Consumers:** Overkill in operational complexity for simple point-to-point task queues; cannot natively manage TTL locks or atomic rate limiting.
- **Temporal / Cadence:** Outstanding for multi-step distributed sagas, but introduces significant infrastructure overhead for our current architectural scope.

## Advantages
- Battle-tested standard in the Python ecosystem with rich documentation and tooling (Flower).
- Reliable task state tracking (`PENDING`, `RUNNING`, `SUCCESS`, `FAILURE`).
- Native task execution time limits (`soft_time_limit`, `time_limit`).
- Seamless worker horizontal scaling.

## Disadvantages
- Celery configuration can be intricate (e.g., prefork vs gevent vs eventlet, late acking).
- Redis as a broker provides at-most-once delivery unless configured with `task_acks_late=True` and idempotent task design.

## Consequences
All Celery tasks must be strictly **idempotent**. State changes must be persisted in PostgreSQL. A dedicated watchdog task will reconcile orphaned jobs if a worker process crashes mid-experiment.

## Status
**Accepted**
