# ADR-004: Kubernetes Isolation Strategy

## Context
Tenants need isolated environments to deploy microservices and inject destructive faults (network drops, latency, CPU starvation) without impacting other tenants or the platform control plane.

## Problem
How to provide multi-tenant workload isolation on Kubernetes that is fast to spin up, cost-effective for local development (Kind) and CI/CD, yet fortified with strong network and resource boundaries.

## Decision
Adopt **dynamic Kubernetes Namespaces** fortified with **ResourceQuota**, **LimitRange**, and **default-deny NetworkPolicy** resources per sandbox. Control plane components run in a dedicated namespace (`chaos-control-plane`) completely unreachable from sandbox pods.

## Alternatives Considered
- **Separate Physical Clusters per Tenant:** Maximum hardware isolation, but economically infeasible, slow to provision (5-15 minutes), and impossible to run locally in Kind for development.
- **Virtual Clusters (vCluster):** Better API isolation than plain namespaces, but adds control plane overhead and complexity for local developer workflows.
- **Unrestricted Shared Namespaces:** High risk of cross-tenant interference and noisy-neighbor resource starvation.

## Advantages
- Rapid provisioning ($< 2\text{ seconds}$ to create namespace and policies).
- Identical behavior across local Kind clusters, on-prem Kubernetes, and managed cloud providers (EKS/GKE).
- ResourceQuota prevents CPU/RAM starvation of host nodes.
- NetworkPolicies enforce strict zero-trust isolation between sandboxes.

## Disadvantages
- Namespaces share the underlying Linux host kernel. Malicious kernel exploits could theoretically escape containers if pod security standards are violated.

## Consequences
Every sandbox namespace will be labeled with `pod-security.kubernetes.io/enforce: baseline`. Pods are forbidden from running as root, mounting host paths, or utilizing host networking.

## Status
**Accepted**
