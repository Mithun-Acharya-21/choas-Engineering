# ADR-006: Chaos Experiment Execution

## Context
The platform must reliably inject network degradation (latency, jitter, packet drop, bandwidth limits) and resource saturation into running sandbox microservices.

## Problem
Many Kubernetes chaos tools require root privileges, host kernel modifications (`iptables`, `tc/netem`), and cluster-wide DaemonSets that can corrupt the host node and leave lingering faults if the orchestrator crashes.

## Decision
Use **Toxiproxy sidecar containers** for layer-4/7 network fault injection, and **ephemeral quota-bounded stress containers** (using `stress-ng`) for compute/memory saturation.

## Alternatives Considered
- **Chaos Mesh / LitmusChaos:** Feature-rich, but require installing intrusive Custom Resource Definitions (CRDs), privileged DaemonSets, and host kernel access (`CAP_NET_ADMIN`), introducing security risks in multi-tenant environments.
- **Istio Service Mesh Fault Injection:** Heavyweight; requires running Istio control plane (Istiod) and Envoy sidecars, tripling memory usage per pod.
- **Pumba:** Modifies Docker/container network namespaces directly on the host, requiring mounting the Docker socket inside the container (major security vulnerability).

## Advantages
- **Zero Host Privileges:** Toxiproxy runs as an unprivileged container in user-space inside the pod.
- **Instant Clean Recovery:** Toxics are managed via REST API. Deleting a toxic immediately restores normal traffic flow.
- **Safe Failure Mode:** If Toxiproxy crashes, the TCP socket is closed; it never silently corrupts the host network stack.
- **Deterministic Calibration:** Microsecond-precise latency and configurable probability toxicity.

## Disadvantages
- Adds a small proxy hop overhead ($\approx 1\text{ms}$) per request.
- Requires traffic routing to pass through the Toxiproxy port.

## Consequences
Every deployment manifest generated by the `SandboxManager` will inject a Toxiproxy sidecar alongside the main application container.

## Status
**Accepted**
