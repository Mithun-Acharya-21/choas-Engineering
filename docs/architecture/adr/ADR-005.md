# ADR-005: Observability Architecture

## Context
Incident detection and root cause analysis require high-fidelity metrics, distributed traces, and container logs from microservices running inside sandboxes.

## Problem
We need an observability pipeline that is open-source, vendor-neutral, supports automated metadata enrichment (injecting `tenant_id` and `sandbox_id`), and provides programmatic APIs for algorithmic incident analysis.

## Decision
Adopt **OpenTelemetry** as the instrumentation standard. Sandbox microservices emit OTLP traces and metrics to a centralized **OpenTelemetry Collector**, which enriches telemetry and routes metrics to **Prometheus**, distributed traces to **Jaeger**, and logs to **Loki**.

## Alternatives Considered
- **Direct Scraping by Prometheus without OTel Collector:** Fails to provide centralized trace forwarding, batching, and tenant metadata enrichment outside the application containers.
- **Commercial SaaS (Datadog/Dynatrace/New Relic):** Cost-prohibitive for high-cardinality ephemeral chaos environments, closed-source, and cannot run locally in Kind/Docker.
- **Grafana Tempo instead of Jaeger:** Great for massive-scale trace storage, but Jaeger provides immediate search indexing by service, tags, and duration out-of-the-box via clean REST APIs needed by our RCA engine.

## Advantages
- CNCF open-standard telemetry ingestion.
- Zero vendor lock-in.
- In-flight attribute enrichment (`tenant_id`, `sandbox_id`, `experiment_id`) via OTel Collector processors.
- High-performance query APIs (PromQL for metrics, Jaeger REST for trace span trees).

## Disadvantages
- Running Prometheus, Jaeger, Loki, and OTel Collector adds local Docker resource overhead ($\sim 1.5\text{GB}$ RAM).

## Consequences
All microservice workloads deployed into sandboxes will be instrumented using standard OpenTelemetry SDKs with W3C trace context propagation.

## Status
**Accepted**
